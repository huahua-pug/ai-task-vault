# ai-task-vault · AI 断点续跑仓库

任何能读写本地文件的 AI Agent（ZCode、Codex、Trae、Cursor、Claude Code、Hermes 等）都可使用本仓库。用法：让 Agent 先完整读取本文件，再按下方规则执行任务。

## 固定文件（禁止改名）

- `task.md` — 任务主输出文档。只追加，禁止删除或改写历史内容；新产出以 `## {子任务名} · {日期}` 标题追加到文末。
- `plan.md` — 子任务清单。状态仅 `[未完成]` / `[已完成]` 两种标记。
- `checkpoint.md` — 断点快照。中断恢复的唯一依据；每完成一个子任务整文件覆写更新，保持小体积。
- `README.md` — 本文件，流程规则。

## 工作流程

1. 动手前先读 task / plan / checkpoint 三份文件。checkpoint 的"任务状态"不是"未开始"即为恢复场景：直接接续"下一个待执行子任务"，禁止重复生成已完成内容，并告知用户待执行项。
2. 全新任务：拆解为多个小规模子任务写入 plan.md，commit 备注 `init:生成任务执行计划`，随后执行第一个子任务。
3. 每轮只执行 1 个子任务，禁止一次跑完全部。完成后依次：结果追加进 task.md → plan.md 标记 `[已完成]` → 覆写 checkpoint.md（时间、最后完成项、下一个待办、状态）→ commit 备注 `checkpoint:完成子任务-{名称}`。
4. 提交后尝试 `git push`：失败（网络/超时）只提示一句"已存本地，下次续跑时自动补推"，不反复重试，不因此中断流程。
5. 每轮结束输出简短进度摘要（已完成 / 下一个待执行），等待用户说"继续"再跑下一项。

## 硬性规则

- 单轮输出体量克制，宁可多分几片，防 token 截断。
- 未读到 plan / checkpoint 不得臆测历史进度，先读文件再动手。
- 全部子任务完成后 commit 备注 `task-finished:任务全部完成`，并输出完整任务总结。

## 任务完成后的归档

全部子任务标记 `[已完成]`、输出任务总结后，执行归档收尾，让三件套干净地迎接下一个任务：

1. 在仓库内创建 `archive/` 文件夹（首次归档时自动创建）。
2. 将 task.md 全部内容另存为 `archive/{YYYY-MM-DD}-{任务名}.md`，文件首行加标题 `# {任务名} · 完成于 {日期}`。
3. 将三件套重置回初始模板（见下）。
4. commit 备注 `archive:{任务名}`，随后照常尝试 push。

归档文件仅供查阅，新任务初始化时不读取。初始模板：

**task.md**
```
# AI任务主输出文档
```

**plan.md**
```
# 任务执行计划

总目标：尚未设置

## 子任务列表

- [未完成] 待填充子任务
```

**checkpoint.md**
```
# 断点检查点

最后更新时间：
最后完成子任务：
下一个待执行子任务：
任务状态：未开始
```

## 手动模式（网页版 AI，无文件读写能力时）

每完成一个子任务，输出三块文本供用户复制粘贴到 GitHub 仓库对应文件：

```
====task.md 新增部分====
【只输出本轮新增的段落，用户粘贴到 task.md 文末】
====plan.md====
【全文】
====checkpoint.md====
【全文】
```

恢复任务时，用户把 GitHub 上三份文件内容粘贴给 AI，AI 解析后接续未完成子任务，禁止重复已生成内容。
